1-1. 요청 배경과 전체 구매·열람 흐름

핵심 문제 정의 · 출처 README §1~2, 01 §1

사료편찬위원회는 『정토대전』 4권 세트(책정가 200,000원)를 외부 서점에 유통하지 않고 정토회원에게만 판매하려 합니다. 시스템국에 의뢰한 검토는 두 가지입니다. ① 구매 과정에 회원인증을 넣을 수 있는가, ② 자체 e북을 만들어 제공할 수 있는가(기술 가능성·범위·인력·기간·수용 여부). 아래는 회원이 책을 사서 e북을 읽기까지의 4단계입니다.

Stage 1 · 회원 접속

마이정토 로그인

기존 로그인 세션과 회원 정보를 그대로 씁니다. 별도 회원가입·SMS 본인인증·자격 검증을 새로 만들지 않습니다.

Stage 2 · 구매·결제 (Phase 1)

임시 구매 메뉴 + PG 결제

회원정보 자동 입력, 도로명 배송지 검색, 카드결제 + PG 가상계좌(입금 자동 확인 웹훅). 관리자는 송장용 주소록 엑셀과 정산 대사 도구를 씁니다.

Stage 3 · 열람권 발급

결제 확정 → 열람권(Entitlement)

결제·취소 웹훅을 중복 없이(멱등) 처리해 권별 열람권을 만들고 회수합니다. 첫 열람 시각(ReadingStart)을 법적 증빙으로 기록합니다.

Stage 4 · e북 열람 (Phase 2)

PDF.js 웹 뷰어

CloudFront 단기 서명(TTL 5분)으로 비공개 S3 원고를 스트리밍합니다. 다운로드·인쇄 버튼을 없애고 회원 식별코드 워터마크를 화면에 겹칩니다.

검토 2 · 판정: 조건부 가능 (2단계 분리 권고)

자체 e북 뷰어 제작이 가능한가?

  • 기준안 P2: Mozilla 오픈소스 PDF.js 기반 무설치 HTML5 웹 뷰어 (솔루션 비용 0원).

  • 대안 P4: 강한 보안이 필요하면 상용 솔루션(유니닥스 ezPDF 등)을 구매해 마이정토 SSO로 연동합니다.

1-4. 초기 통념 9가지와 실제 실행 기준

출처 01 §1.2
# 초기 통념 실제 엔지니어링·법무 기준
1"PDF 단순 다운로드는 공수가 거의 없다"파일 배포 외에도 권리 확인, 회원 자격 검증, 결제·환불 연동, 정오표 파일 교체, CS 대응 도구가 함께 필요합니다.
2"웹 뷰어로 만들면 파일 유출이 완전히 차단된다"로그인·서명 URL은 권한 없는 외부인만 막습니다. 권한 있는 브라우저로 전송된 PDF·텍스트 추출이나 화면 촬영은 막지 못합니다. 완전 차단이 목적이면 P4(상용 DRM)나 P5(전용 앱)가 필요합니다.
3"본문 검색이 필수면 EPUB(P3)이어야 한다"텍스트 레이어가 있는 인쇄용 PDF + PDF.js(P2)로 권 내 검색이 됩니다. 글자 크기에 따른 줄바꿈 재배치(Reflow)가 필수일 때만 P3가 필요합니다.
4"우클릭·복사·인쇄를 막으면 DRM이 해결된다"선량한 사용자의 실수를 막는 UI 억제책입니다. 서버 권한 검사나 암호화 DRM을 대체하지 못하며, 키보드·스크린리더 접근성 훼손도 함께 점검해야 합니다.
5"InDesign 원고가 있으니 EPUB이 바로 나온다"내보내기 시 스타일·읽기 순서·복잡한 표·각주·한자 이체자가 깨집니다. 별도 XHTML 구조화와 전수 편집 검수 비용이 듭니다.
6"오프라인 열람은 PWA로 만들면 된다"PWA 캐시는 환불 시 파일 회수, 암호화, 기기 인증을 보장하지 않고, 브라우저 용량이 부족하면 임의 삭제됩니다.
7"권리 정리 전에는 아무 개발도 못 한다"실제 원고의 반입·변환·공개는 금지하지만, 허가된 더미(샘플) 원고로 인증·결제·뷰어 PoC를 먼저 개발하는 것은 가능합니다.
8"e북은 구매 후 환불 불가가 원칙이다"청약철회를 제한하려면 구매 전 명확한 고지, 샘플(미리보기), 실제 첫 열람(ReadingStart) 서버 로그가 법정 요건을 충족해야 합니다.
9"한 번 사면 영구 열람을 보장한다"이용권의 유효기간과 서버 서비스의 지속 의무를 구분해 약관에 적고, 서비스 종료 시 사전 고지·대체 제공·보상 원칙을 미리 정해야 합니다.
💡 [표를 쉽게 읽는 핵심 해설]

① 보안(2·4번, 붉은 행): 결론은 같습니다. 웹 기술로는 화면에 보이는 콘텐츠의 복제를 완전히 막을 수 없습니다. 그래서 P2 채택에는 "한계 수용" 서명(D2)이 붙습니다.

② 형식(3·5번): 이미 조판된 PDF를 그대로 쓰는 것이 EPUB 변환보다 비용이 적다는 점이 P2 기준안의 근거입니다.

③ 일정(7번, 초록 행): 권리 확인을 기다리는 동안 더미 원고로 PoC를 진행할 수 있어, 권리 문제가 개발 착수를 완전히 막지는 않습니다.

03 §2.2 renderPageHiDPI()

입력: pdfDoc, pageNum, scale, canvas
출력: 기기 픽셀 밀도에 맞춘 선명한 캔버스

  1. devicePixelRatio(Retina 2.0~3.0)를 읽음
  2. 내부 버퍼 = 논리 크기 × 배율, CSS 크기는 논리 크기로 고정

const pixelRatio = window.devicePixelRatio || 1;
const viewport = page.getViewport({ scale });
canvas.width  = Math.floor(viewport.width  * pixelRatio);
canvas.height = Math.floor(viewport.height * pixelRatio);
canvas.style.width  = `${Math.floor(viewport.width)}px`;
canvas.style.height = `${Math.floor(viewport.height)}px`;
const transform = pixelRatio !== 1
  ? [pixelRatio, 0, 0, pixelRatio, 0, 0] : null;
await page.render({ canvasContext: ctx, transform, viewport }).promise;

03 §4.2 issueReaderSession() 의사코드 (요약 발췌)

입력: request.volumeId, authSession
출력: sessionId, contentVersionId, signedUrl(5분), watermarkCode

member = verifyMemberStatus(authSession.memberId)
volume = db.findVolume(Whitelist(request.volumeId))
LOCK(member.id, volume.id)
ents = db.findEntitlements(member, volume,
         status='ACTIVE', startsAt <= NOW(),
         expiresAt IS NULL OR expiresAt > NOW())
IF ents.isEmpty(): RETURN Error(403, "ERR_NO_ENTITLEMENT")
ver = db.findApprovedContentVersion(volume.currentVersionId, status='READY')
session = db.createReaderSession(member.id, volume.id, ver.id, ttl=5m)
signed = cloudfront.sign(ver.assetKey, NOW()+5m)
RETURN {session.id, ver.id, signed,

③ 복구 훈련은 출시 후에도 반복: 출시 전 1회(DR-01)로 끝나지 않고 분기마다 다시 합니다.

6-6. 8대 비상 사건별 초동 조치와 금지 행위

출처 04 §5
비상 사건초동 조치하지 말 것
1. 타 회원 정보·워터마크 혼입해당 API/CDN 경로 차단 → 로그·증거 보존 → 개인정보 책임자 이관임의 로그 삭제, 사실 확인 전 성급한 공지
2. 비공개 S3 원고 노출버킷 정책·OAC 잠금 → 서명 키 교체 → 노출 범위 파악"CDN 캐시를 지웠으니 회수됐다"는 허위 보고
3. 결제 후 열람권 미부여 다발신규 결제 보류 검토 → 원장 대사 워커 → CS 공지검증 없이 문의자 전원에게 영구 권한 지급
4. PG 취소 API 타임아웃REFUND_UNKNOWN으로 두고 PG 조회로 확인새 멱등키로 취소 무한 재요청(중복 환불)
5. 배포 직후 오류율 급증서킷 브레이커 또는 직전 이미지 digest로 앱 롤백앱 오류인데 DB까지 과거로 덮어쓰기
6. 잘못된 원고 배포current_version_id를 직전 승인 버전으로 롤백운영 S3 파일 수동 덮어쓰기
7. DB 손상·오삭제쓰기 제한 → 격리된 새 DB에 PITR → 원장 대사 후 전환정상 결제 기록이 있는 운영 DB를 백업으로 통째 덮어쓰기
8. 대량 다운로드·스크래핑계정 세션·IP 레이트 리밋 → 증거 로그 확보워터마크 코드 하나로 피해 회원을 범인으로 단정
출시 전 격리 DB 복구 훈련 6단계 (DR-01)
  1. 외부 통신을 끊은 격리 환경에 스냅샷으로 새 PostgreSQL 시점 복원
  2. 회원 매핑·주문·열람권·북마크 건수 확인, 백업 이후 PG 승인·취소 내역 추출
  3. 원장 대사로 백업 이후 거래를 재반영해 중복·누락 확인
  4. S3 원고 해시와 CloudFront 서명 키 연결 점검
  5. 실측 RTO(목표 4시간)·RPO(목표 15분) 기록
  6. 백업에서 되살아난 탈퇴 회원 정보 재삭제(Re-purge) 확인 후 환경 파기

① 금지 열의 공통점: 급할 때 하기 쉬운 "덮어쓰기"와 "일괄 지급"입니다. 8건 중 3건(5·6·7번)이 덮어쓰기 금지입니다(3/8건).

② 롤백 범위를 나눔: 앱 문제는 앱만, 원고 문제는 매니페스트만, 데이터 문제는 격리 DB 복원으로 대응합니다.

③ 워터마크의 한계: 코드가 찍힌 캡처가 나와도, 계정 탈취 피해자일 수 있으므로 바로 범인으로 단정하지 않습니다.

📌 [탭 6 축약어 및 학술 용어 주석 (Glossary)]
• Go / No-Go: 출시 직전 진행 여부를 최종 결정하는 회의.
• Kill Switch: 미리 정한 임계를 넘으면 배포를 즉시 멈추고 되돌리는 기준.
• 이미지 digest: 컨테이너 이미지의 고유 해시. 같은 digest면 같은 코드가 배포됩니다.
• PITR: 특정 시점으로 DB를 복원하는 기능(Point-In-Time Recovery).
• RPO / RTO: 잃어도 되는 데이터 시간 / 복구에 걸려도 되는 시간의 목표치.
• pageMap: 개정 전후의 쪽번호 대응표. 기존 북마크를 새 판의 같은 위치로 옮깁니다.
